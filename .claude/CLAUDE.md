# AI Code Assistant: Secure Flask Blog Project Instructions

- Review and remove any uses of debug mode; ensure production runs never set debug=True.
- Disallow unsafe file/path handling and enforce filename/path validation to prevent path traversal.
- Forbid raw SQL string concatenation; require parameterized queries or an ORM to prevent SQL injection.
- Enforce safe template rendering and sanitization for user-provided HTML to prevent XSS.
- Prohibit use of eval/exec/os.system or similar with user input; require explicit alternatives and secure headers/CSP.
- Require static-analysis/CI checks (linters, bandit, SAST) before merging code generated by the assistant.

## Project Overview (Concise)
This repository is a small Flask blog: create, view, delete posts. Posts are stored in memory (no DB by default). The AI Code Assistant will generate and update Python/Flask code and templates. All generated code must follow the security rules below to avoid introducing vulnerabilities (path traversal, debug mode, SQL injection, XSS).

## Mandatory Security Policies for the AI Code Assistant
The assistant must follow these rules whenever generating or modifying code in this repo:

- Never enable Flask debug mode in code committed for production. Do not output `app.run(debug=True)` or equivalent in any committed files. Use environment-controlled flags and document safe defaults.
- Never use unsanitized path or filename values from requests to read/write files. Always validate and normalize file paths and use secure utilities.
- Never construct SQL queries by concatenating strings with user input. Use parameterized queries or an ORM (e.g., SQLAlchemy) exclusively for database access.
- Never render raw user-supplied HTML without sanitization. Rely on Jinja2 autoescape by default; if allowing HTML, sanitize with a vetted sanitizer (e.g., bleach) and only mark content as safe after sanitization.
- Never emit code that uses eval(), exec(), os.system(), subprocess with shell=True, or other dynamic execution primitives on user-controlled input. If a use-case truly requires it, require an explicit security review and strict input validation.
- Validate all route parameters (types, regex, ranges) and fail safely (400/404) on invalid input.
- Use secure headers (Content-Security-Policy, X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy) on responses by default.
- Store secrets only in environment variables or secret stores. Do not hardcode secrets, API keys, or credentials in generated code.

## Secure-by-Default Code Patterns (Examples)

- Preventing debug mode in app startup:
```python
# python
import os

if __name__ == "__main__":
    # Do NOT set debug=True here. Use environment variables for development only.
    debug = os.environ.get("FLASK_DEBUG", "0") == "1"
    # In production CI/CD, ensure FLASK_DEBUG is unset or "0".
    app.run(host="0.0.0.0", port=int(os.environ.get("PORT", 5000)), debug=False)
```

- Secure file uploads/downloads and path traversal mitigation:
```python
# python
import os
from werkzeug.utils import secure_filename
from flask import request, abort, send_from_directory

UPLOAD_DIR = os.path.join(app.instance_path, "uploads")
os.makedirs(UPLOAD_DIR, exist_ok=True)

def is_within_directory(base_dir, target_path):
    base_dir = os.path.realpath(base_dir)
    target_path = os.path.realpath(target_path)
    return target_path.startswith(base_dir + os.sep)

# Handling an uploaded file
file = request.files.get("file")
if not file:
    abort(400)
filename = secure_filename(file.filename)
if not filename:
    abort(400)
target_path = os.path.join(UPLOAD_DIR, filename)
if not is_within_directory(UPLOAD_DIR, target_path):
    abort(400)
file.save(target_path)

# Serving a file securely
@app.route("/uploads/<filename>")
def download_file(filename):
    # Avoid exposing file paths. Use send_from_directory which guards paths.
    safe_name = secure_filename(filename)
    return send_from_directory(UPLOAD_DIR, safe_name, as_attachment=True)
```

- Parameterized queries (avoid SQL injection) — sqlite3 example:
```python
# python
import sqlite3

def get_posts_by_author(conn, author):
    # NEVER: f"SELECT * FROM posts WHERE author = '{author}'"
    cursor = conn.execute("SELECT id, title, body FROM posts WHERE author = ?", (author,))
    return cursor.fetchall()
```

- Using SQLAlchemy (recommended) to avoid raw SQL:
```python
# python
from sqlalchemy import Column, Integer, String, Text
from sqlalchemy.orm import declarative_base, Session

Base = declarative_base()

class Post(Base):
    __tablename__ = "posts"
    id = Column(Integer, primary_key=True)
    title = Column(String(200))
    body = Column(Text)

# Querying safely:
# session is a SQLAlchemy Session
posts = session.query(Post).filter_by(author=author).all()
```

- XSS prevention and safe rendering:
```python
# python
from bleach import clean

# Sanitize user input if HTML must be allowed. Define allowed tags/attrs conservatively.
ALLOWED_TAGS = ["b", "i", "u", "em", "strong", "p", "br", "ul", "ol", "li", "a"]
ALLOWED_ATTRS = {"a": ["href", "rel", "target"]}

def sanitize_user_html(html):
    return clean(html, tags=ALLOWED_TAGS, attributes=ALLOWED_ATTRS, protocols=["http", "https"], strip=True)

# In route:
raw_content = request.form.get("content", "")
safe_content = sanitize_user_html(raw_content)
# Store safe_content or store raw and sanitize upon rendering; never mark as safe without sanitization.

# In template: use normal Jinja2 autoescape
# {{ post.content }}  -> This will be escaped if it's plain text.
# If inserting sanitized HTML and you must mark safe:
# {{ post.safe_html|safe }}  -> Only allowed when safe_html is sanitized as above.
```

- Add security response headers (Flask after_request example):
```python
# python
@app.after_request
def set_security_headers(response):
    response.headers.setdefault("X-Content-Type-Options", "nosniff")
    response.headers.setdefault("X-Frame-Options", "DENY")
    response.headers.setdefault("Referrer-Policy", "no-referrer")
    # Set a restrictive CSP; adjust according to app's needs.
    response.headers.setdefault("Content-Security-Policy", "default-src 'self'; script-src 'self'; object-src 'none';")
    return response
```

## Rules Specific to Preventing Each Reported Vulnerability

- Path Traversal (CWE-23)
  - Always use secure_filename() for any filename coming from a request.
  - Use a fixed upload/download base directory (inside app.instance_path or a configured directory) and verify resolved real paths start with that base directory.
  - Never accept arbitrary file paths or path segments (e.g., `../../etc/passwd`) from clients.
  - Prefer send_from_directory for serving files; never call open() on a user-provided path without realpath validation.

- Debug Mode Enabled (CWE-489)
  - Never commit code that sets debug=True.
  - Default runtime MUST be non-debug. Ensure CI/CD runners and production Docker/Gunicorn configs explicitly disable Flask debugging.
  - If generating development convenience code, include comments and guard it so debug can only be enabled locally via environment variables and is not present in committed production config.

- SQL Injection (CWE-89)
  - Disallow raw string concatenation for SQL queries in generated code.
  - Prefer using an ORM (SQLAlchemy). If using DB-API directly, always use parameterized queries (placeholders).
  - Validate and sanitize parameters (types and lengths) before passing them to queries.
  - If the repository currently has no DB, avoid adding one without specifying secure access patterns abiding by above rules.

- Cross-site Scripting (XSS) (CWE-79)
  - Rely on Jinja2 autoescape for all templates. Never turn autoescape off globally.
  - Do not use the `|safe` filter on untrusted data. Only use it on content that has been sanitized with a vetted library (bleach) and explicitly reviewed.
  - Use Content-Security-Policy headers and the other security headers shown above.
  - Validate and constrain HTML inputs (whitelist tags and attributes) if HTML post content must be allowed.

## AI Code Assistant Generation Constraints (Hard Requirements)
When the AI assistant generates code for this repo, it must include or adhere to:
- Explicit input validation for every request parameter and file field.
- Examples or comments in generated endpoints that describe why validation/sanitization is applied.
- No use of eval(), exec(), os.system(), subprocess with shell=True, or similar with data coming from request or environment unless the code includes a clear, auditable justification and a safe-guarded validation path (and then requires human review).
- No hardcoded secrets. Use os.environ.get("MY_SECRET") and document required environment variables in requirements or README.
- Generate tests for any new input-handling endpoints focusing on security (e.g., attempting path traversal, SQL injection payloads, XSS payloads) or add instructions to run security scans.
- When adding database access, include examples of parameterized queries and a recommendation to use SQLAlchemy with session management and migrations.

## Deployment & Runtime Guidance
- Development: set FLASK_ENV=development and FLASK_DEBUG=1 only on local machines; never commit code that turns these on for deployed environments.
- Production: run with a WSGI server (e.g., gunicorn). Example:
```bash
# Run in production (example)
gunicorn --bind 0.0.0.0:${PORT:-8000} app:app
```
- Ensure environment variables for secrets, debug flags, and configuration exist and are documented:
```bash
# required env vars
FLASK_ENV=production
FLASK_DEBUG=0
SECRET_KEY=<set via env>
```

  - Static analysis / SAST (e.g., semgrep, bandit).
  - Dependency checks (safety, pip-audit).
  - Linting (flake8/black) and unit tests that include security-focused tests where applicable.
- Include an automated check that rejects code containing forbidden patterns (e.g., `debug=True`, `eval(`, string-sql concatenation patterns, accessing file paths directly from request without secure_filename).
